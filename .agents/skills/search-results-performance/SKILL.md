# Search and results performance

Keep result correctness and responsiveness together. Read only the affected source paths and, for measurements, [references/benchmarks.md](references/benchmarks.md). Do not require the historical performance analysis or a full audit for every edit.

## Optimize outcomes, not the current implementation

Better performance is always allowed. The mechanisms, budgets, TTLs and examples below describe the current design and lessons from measurements; they are not permanent architectural requirements or performance ceilings. Replace or simplify them when a better approach meets the task's intended behavior. Do not require separate approval merely to improve performance within the authorized scope.

Evaluate latency, VPS load, transferred data, provider usage and result quality together. Fewer SQL/provider calls are useful signals, not absolute goals: additional cheap queries or bounded parallel requests can be a net improvement. Likewise, changing a budget, cache strategy or retrieval boundary is allowed when its effect on coverage, freshness and ordering is understood and verified. Honor intentional user-requested behavior changes rather than demanding identical old results.

## Query and payload cost

- Count SQL statements **and** inspect transferred rows/columns and deserialization. A cached summary does not help if every poll still selects the full filmography JSON. The measured large-credit bottleneck was payload transfer, even with only four SQL reads.
- The current `backend/core/contributor_evidence.py` avoids repeated credit-payload transfer by reading evidence headers and reusing policy/role summaries. This is one effective approach, not a required two-step query design. Fetch only the data needed to establish eligibility/freshness. Requesting uncached summaries for irrelevant roles defeated mixed-search cache hits; preserve that lesson when replacing the mechanism.
- Keep private policy reads focused. `viewer_policies` currently shares one vote/popularity read across default sections, and editor/list state is attached to displayed cards together. Prefer equivalent batching/reuse over enriching full pages and discarding most cards; useful prefetch for the next interaction remains allowed.
- Preserve complete underlying domain records where the product requires them; search-only evidence may use bounded samples/projections. Indexed existence checks currently avoid transferring entire local works or querying once per credit. Alternative indexes, summaries or batching are welcome when they preserve the required evidence.

## Provider retrieval and enrichment

- Apply known adult/anime/category/runtime/popularity violations before expensive details. Handle missing evidence according to the result contract: titles may need enrichment, while unverified contributors may be temporarily omitted. Do not treat missing summary fields as proof of a negative or silently drop required filter checks.
- Prefer reusing or improving TMDB's shared request layer, concurrent-request coalescing, and base/appended component caches over adding duplicate retrieval paths. Compose a requested detail shape only when the base and **all** requested components are valid for its parameters/language. A cache hit alone does not establish renewed freshness; TTL changes or revalidation policies need explicit freshness reasoning. Do not mix failed credentials with another caller's in-flight request.
- Studio verification currently uses popularity-sorted samples bounded across worker ticks (two discovery pages per media kind per candidate); people share combined credits across actor/crew. Keep resource use controlled, but improve sampling, ordering or budgets when measurements and relevance checks support it. These numbers are not fixed limits for future designs or other subsystems.
- Chronological selection and text search have different ordering/coverage contracts. Shared evidence, precomputed indexes or merged retrieval are allowed. Current timelines finalize a bounded window before paging; changing the selection must account for stable paging and required country evidence, rather than silently sacrificing them for a timing.

## Cache, policy and failure semantics

- Share public provider evidence across viewers; scope private result/editor state to its viewer. Any eligibility cache must account for inputs that affect its answer, currently evidence identity/expiry, candidate role, effective policy and anime visibility. Reevaluate when these inputs change, without repeating valid provider discovery.
- Preserve unknown, partial, verified-empty and failed states. A complete negative can be reused until expiry; a timeout is not proof of irrelevance. Avoid repeating an expired slow check in every request; deduplicated refresh is the current solution, and alternative freshness strategies are allowed.
- Keep resource use bounded and shared-work ownership/cancellation correct. Queue admission and leases are current mechanisms, not mandatory architecture. A departing caller must not cancel another subscriber's needed work or poison retry state.
- Runtime enrichment has a short retry cooldown after failure/budget exhaustion. Unknown runtime remains unknown; local/durable runtime still wins, credentials remain isolated, and ordinary caller cancellation does not set a cooldown. Do not cache a provider outage as a successful empty search.
- Keep curation distinct from explicit user filters. Show all bypasses personal restrictions without changing account settings, the query/scope/sort or explicit filters. Adult/anime rules remain in force. It is not a quick-search feature. MDBList ranked feeds already supply curation and are exempt from TMDB popularity/vote floors; do not blanket-exempt other restrictions.

## Games detail pages

- Exclude verified mobile-only games and mobile-specific port records from independent discovery/mapping/import eligibility. Keep mixed PC/console titles and dedicated handheld consoles; a phone port must not add a mobile tag to its desktop/console parent. Use exact IGDB platform evidence (including Legacy Mobile Device) and retain original platform evidence separately from the displayed non-mobile platforms. Missing platforms remain unknown. Filter excluded candidates before expensive corroboration, company document ingestion and related-card publication; apply the same stored policy to contributor qualification and detail/tracking capabilities. Changes to mobile eligibility must cover same-name desktop/mobile candidates, mixed releases, explicit ports, cached pages, and contributor search-index refreshes.

- Exercise cold Steam-imported games as well as IGDB-backed portfolio stubs. A Steam identity alone cannot enter the IGDB primary loader. Legacy orphan repair runs only through an explicit Admin Data Health scan and confirmed reconciliation (or the manual operator CLI), never imports, detail visits or scheduled metadata jobs. Scan bounded batches against exact IGDB external-game references; distinguish missing, failed, incomplete and ambiguous evidence. Recheck identity ownership when applying a fresh server-stored scan. Preserve imported roots, private tracking, protected edits, credits, performances, permanent old-URL aliases and provisional/source-cache references; conflicting private decisions require review. Canonical game primary metadata still uses its existing background acquisition path.
- Steam review exposes the library immediately, including selectable pending mappings. Preparation batch-checks exact IGDB app references, skips provider work for indexed Steam identities already attached to IGDB games, and persists public classification evidence. Polling distinguishes pending, ready and unavailable mappings; unavailable cards reject selection while verified combined-game components remain independently selectable. Import resolves its selected pending mappings outside owner/connection locks, then revalidates generation and ownership before saving. Every new imported membership, including reviewed component/progress targets and auto-add, requires a canonical IGDB identity; failed/unmatched apps are skipped without creating Steam-only roots. Recent complete positive classification (currently 30 days) creates both identities atomically or attaches Steam to an existing IGDB root under the catalogue write lock. Sparse company/person discovery and provisional bulk headers reuse a verified legacy Steam root before allocating a new root, but never merge two existing roots automatically. Existing duplicates remain for manual admin reconciliation. Legacy Steam-only metadata jobs are retired by mt078; full primary metadata and optional characters must not be fetched for an entire library just to classify it. Cover early import, late preparation completion, negative/ambiguous/capped evidence, indexed identity reuse and independent component selection in disposable PostgreSQL tests and rendered picker checks.
- Keep primary game metadata and usable cast projections independent of optional portraits, galleries, prices and career enrichment. Paint saved artwork first; request missing portraits for visible people, and expose character art and extra galleries on demand. The eight-person preview is a presentation budget, never a limit on stored or accessible credits.
- Steam software exclusions use exact IDs from the public software-only GetAppList feed, shared for one day with a retry cooldown on failure. Known software is hidden on opening the picker and disabled through progress updates if classification finishes later. Positive software evidence takes priority over IGDB/component mappings and is enforced before retarget, import and auto-add writes; reject it before IGDB/achievement fan-out. Absence from the software feed is unknown, not proof of a game. Preserve the existing canonical IGDB admission requirement.
- Steam Store redirect fallback runs only after a fresh, complete IGDB miss, with no existing canonical identity, progress target or reviewed component. Never probe excluded software, packs/mods, ambiguous or incomplete evidence. Fetch only first-response headers, accept an explicit HTTPS Steam Store redirect to a different app ID, and verify its exact unambiguous independent IGDB game before publishing the existing progress-target relationship. Cache redirect observations/misses for 30 days with shared leases and a 15-minute failure cooldown. Bound parallel checks, recheck source/target evidence under the catalogue lock, retain separate app counters and never treat the redirected app as an equivalent provider identity.
- For missing person portraits, reuse a known TMDB identity before doing an IMDb-ID lookup. TMDB find results can supply `profile_path` without a second profile request. Keep that portrait projection separate from canonical identity merging, which retains its stronger reverse-ID checks. Avoid fetching filmographies, image galleries or Wikidata evidence merely to show a headshot.
- Bound portrait concurrency across batches (currently four TMDB lookups per event loop), coalesce overlapping people, and cache positive and verified-empty outcomes durably. Preserve timeouts/errors as retryable evidence, keep stale usable artwork, and batch only the remaining missing pictures through IMDb. Recheck identities and protected edits after provider I/O; no background portrait should replace an already usable image in the mounted page.
- Run `game_credits` separately for the complete cast/character projection, and `game_portraits` for eight-person acquisition, warm cache cost and provider fan-out. Include focused timeout, partial failure, cancellation, alias/edit and authorization checks. Distinguish controlled ASGI timings from live-provider and browser download/decode measurements; neither establishes complete authenticated page paint time.

## Games contributor cold loads

- Contributor status separates `works_pending` from source validation, person identity and `characters_pending`. The heading shows animated “Fetching X / Y”; Y is a changing candidate upper bound, not raw provider-credit count or a promised final total. Hide its denominator while source coverage is unknown. Reuse the page's known work count; status-only polls calculate it independently without transferring filmographies. Once missing-work acquisition settles, validation/caption polling continues silently and corrections still reconcile. Character skeletons require outstanding acquisition or its durable admission handoff; completed empty character metadata must suppress them. Check caption-only polling beyond100 mounted cards, pagination restart, cancellation, reduced motion and authenticated desktop/mobile rendering.
- Person/bulk workers share filtered250-credit IMDb pages through the fresh-only five-minute `game_person_source` cache. Preserve source counts/cursors and shared-loader transport ownership under cancellation; never mix old unfiltered50-credit cursors into this source. Explicit miscellaneous `voice actor:` jobs and the dedicated dubbing category are acting evidence; miscellaneous alone is not. Keep raw jobs/categories separate from normalized retention/source keys. Preserve reviewed main-game and custom parent mappings in benchmarks intended to reproduce an existing portfolio. Compare canonical membership as well as count: additional valid voice works can reach a historical count before every historical work is present. See the benchmark reference for the live Mercer253+4 and shared-source measurements.
- Missing-first bulk reconciliation uses a separate durable `game_person_priority` index; preserve unique review-index rows and freeze scheduling within a source generation. Companies retain accepted involvement IDs in their durable cursor, scan compact headers in500-record groups when bulk evidence exists, and hydrate missing primary/variant records before accepted records. Successful provisional rows retire atomically with mapped-credit publication; exclusions/conflicts retire immediately. Live disposable database samples reached Mercer249 in198.706→61.747s and Activision695 in89.594→4.416s, with monotonic count histories at0.5s observation after the fix. These are single backend samples excluding browser paint and remaining accepted-title verification; Mercer253 remains unreproduced cold. The60-work50ms compatibility run retained fingerprints/payloads, warm reads10 and company3 provider calls; person SQL1797/1038→1792/1034 and company290/316 unchanged. Concurrent tests affected latency (person13.389→16.957s, company1.070→1.586s) and transport batching (94→95 calls, unchanged120 logical IGDB queries); do not claim isolated latency gains from that sample.
- The initial `game_bulk` pass acquires compact public classification/participation headers with a 3.85-second provider deadline, reuses existing IGDB identities and publishes provisional rows separately from verified credits and IMDb bindings. Missing/ambiguous evidence stays unknown. Normal verification retires settled candidates; transient failures retain usable rows. Measure source acquisition, canonical publication, scheduler/provider contention and browser polling separately: the deadline does not guarantee a four-second page paint. Completion queues primary metadata at background priority; opening a game promotes its existing job. Cover late negative publication, canonical/private-state reuse, final-credit projection before hydration, and click priority with the bulk tests.
- Measure a genuinely cold **portfolio**, not just a browser reload or `game_person_cached`. Trace person-source acquisition, title discovery, mapping ingestion, projection publication, scheduler waits and browser reconciliation separately. A fast shell/LCP can coexist with a minutes-long works list. Will de Renzy-Martin's live IMDb source contained 59 distinct game titles and took about four seconds to acquire locally; this alone does not measure complete IGDB matching or beta page loading.
- `game_person_cold` and `game_company_cold` extend `scripts/benchmark_search.py` with 60-work cold workloads, first usable works, complete acquisition, all cursor pages, SQL/index writes, provider requests, payload bytes and warm-read checks. Run them separately from cached/search cases at both 50ms and 750ms provider delays. See the benchmark reference for precisely which provider layers each controls. The current fuzzy-match budget is four titles; cheap explicit identity lookup can cover twenty. Neither budget may truncate the stored career.
- Game title retrieval sends search commands through the ordinary IGDB games endpoint: live multiqueries containing search returned an empty aggregate even when the ordinary search succeeded. Minimal Control/Zelda probes, mixed search/filter batches, content-type changes, real newlines, command order and the search endpoint reproduced the failure; do not call this a verified upstream implementation bug or silently treat it as a no-match. Compatible exact-name/filter branches still share service-scoped IGDB multiqueries of at most ten logical queries; caller order and the existing provider lanes remain intact. Keep each named result, branch completeness, overflow page, alias expansion, remaster/edition identity rule and final merge order intact. Never accept a first hit merely to save queries. Oversized aggregate responses split into smaller requests; malformed, partial or failed batches remain unknown errors. Retain existing durable cache/coalescing and provider budget lanes rather than inventing per-view caches or bypassing throttling.
- Measure physical batch widths before raising the four-title fuzzy-match limit. Durable cache admission can stagger sibling queries: a one-loop flush measured as a two-query request followed by six, spending two turns in the serialized provider lane. The shared collector allows 25ms for competing cache subscribers to arrive; 10ms fragmented overlapping-career batches in the pipeline benchmark. Slow or cached siblings do not hold it indefinitely, and cached hits need no collection window. Preserve first-publication latency, retry/cancellation behavior and the ten-query transport limit when tuning this policy. Stage timings and logical-query/physical-width counters are available in the cold benchmark.
- The discovery pipeline has two worker tasks per process, at most one active leased batch per person, and a shared bounded IGDB dispatcher (32 active/queued request groups, at most ten logical queries per transport call). Atomic oldest-due `SKIP LOCKED` claims prevent workers selecting the same job or waiting behind a locked row. IGDB permits two in-flight requests across workers, with starts still spaced by 300ms and shared cooldowns retained. Other provider lanes remain serialized; different providers and local stages may overlap. Keep catalogue publication in the existing write lane. Pending continuations remain durable database jobs; shutdown cancels workers, releases owned person leases and closes dispatcher futures. Crash recovery retains lease expiry. Check competing and overlapping careers with `game_people_pipeline` and `game_people_pipeline_shared`, not just a single-person benchmark.
- Persist shared per-title mapping outcomes in stable IMDb-ID order even when different careers supply different same-year source orders. Concurrent opposite-order upserts can deadlock and defer a valid portfolio for a retry. Keep source traversal/cursors newest-first; only the shared-row write order is sorted. The reversed-order PostgreSQL regression exercises this contention explicitly.
- Discovery/company portfolios request primary covers and identity/participation facts; optional descriptions and artwork/screenshot galleries belong to game-detail acquisition. Sparse portfolio ingestion must preserve richer/protected metadata already stored. The company cold case measures controlled page ingestion, not real IGDB response payload reduction; verify its query boundary and live provider bytes separately.
- Company acquisition has two leased workers with atomic oldest-due SKIP LOCKED claims. Fresh generations scan compact game-type/version headers, load primary/expansion metadata first, skip verified non-display DLC/update/bundle detail fan-out, and retain port/version participation headers in a durable tail. Unknown types still need metadata and remain partial if unverified. Legacy numeric cursors continue until the next fresh generation. Parent rows are reused only within an owned four-page/55-second acquisition; cancellation resets that scope. Keep source record counts and final port-only parent participation, and test a small company queued behind a large one.
- Source-index contents follow their source generation, not mapping revisions. Reprojection reuses the complete index when its generation matches; stale/missing-generation indexes still rebuild. Prioritize ready credit projections before optional person identity jobs, and drain ready work without a fixed sleep after every successful batch. Keep fair durable admission, leases, provider cooldowns and cancellation recovery.
- Mapping work publishes verified primary identities before slower or earlier unmatched siblings; the durable cursor stays behind unattempted fuzzy work. Deferred IDs receive no negative evidence or retry count. Match at most four fresh candidates after the twenty-title identity group, and order known child/version matching last. Compare canonical membership and release-date groups: equal-date ties use local IDs, so separately seeded cold databases may differ within ties. Retain verified bindings if later acquisition fails. Share byte-identical query strings without merging different candidate scopes; finish terminal exact-name/year ties as unresolved with partial coverage, never as verified or complete. IGDB uses two transaction-owned cross-worker slots and a short shared start reservation; release the rate lock before HTTP while retaining the 300ms start interval and shared cooldowns. Bound local slot waiters before acquiring database connections, and verify slot release on cancellation.
- Credit acquisition and optional person-identity enrichment have independent completion states. Continue compact polling for either while needed, but show “Loading works” only for pending credit acquisition. Do not silently abandon a healthy pending portfolio after twenty status reads. Retry consecutive transport failures with bounded backoff, respect provider retry deadlines, and abort page-owned timers/requests on navigation.
- Verify the actual authenticated contributor page with delayed publication: first cards appear automatically; completed works stop the indicator while identity enrichment may continue; pagination, list filters, timeline/compact layouts, mobile overflow, reload restoration and back/forward remain usable. Unit/ASGI timings do not establish production latency. If live IGDB credentials or beta authentication are unavailable, report that limitation instead of calling controlled results a live cold-load fix.

## Result stability and extension

- Give a primary premiere/season a logical identity that survives corrected dates and richer country metadata. Optional rereleases remain distinct events. When merging local and provider pages, retain fresh-event precedence across the finalized window, not only the current slice; otherwise a cached copy can reappear later. Do not deduplicate by title text or collapse legitimate season/rerelease events.

- Keep title ranking/results stable during progressive people/studio verification. Contributor rows may evolve independently. Do not make background eligibility polls reload or reshuffle titles.
- Tab/view/sort changes must invalidate obsolete requests and show the new view or skeleton promptly. Preserve query ownership, pagination cursors, viewport refill and observer cleanup; stale responses must not overwrite the current selection. Inspect the real page when changing these paths.
- Reuse or improve media/provider and policy/composition boundaries when extending results; do not impose a particular adapter or retrieval topology. Combined movie/series ranking must remain comparable where that behavior is required. Measure added work from new books/games results, and use batching, caching or bounded concurrency where they improve the outcome.

## Verify and maintain

For covered implementation changes, run the existing benchmark at the scope above, before and after, with equivalent fixtures/settings. Run relevant neighboring tests. Compare result identities/order, pagination and pending states as well as counts/timings; explain intentional behavior differences. Investigate extra queries/provider calls and payload growth even if a single latency sample improves. Budget/filter changes may be valid optimizations or requested features; assess their result-quality tradeoffs. Do not hide a regression by weakening the measured workload or claiming a semantic change is an equivalent optimization.

Use the benchmark reference for supported commands, profiles and measurement limits. Keep raw measurements out of Git in a verified ignored location; keep reusable benchmark code and this skill version-controlled. If a required check cannot run, state the missing prerequisite and unverified behavior; never substitute a preview/production test database.

When changing providers, routes, cases, cache semantics, budgets or benchmark instrumentation, check this skill and its reference for drift in the same change. Update only facts demonstrated by code or measurements. Preserve meaningful stress/failure/quality checks; do not replace them with easier fixtures or universal millisecond promises. Report the cases run, SQL/provider/payload changes, result correctness, and whether timings are controlled backend, live-provider or browser measurements.
