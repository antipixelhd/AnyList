# 500-session investigation

Baseline `2763ad5524181fafefc2f81b5996f50fa8615ae7`, branch
`codex/anylist-stress-test`. No beta/production deployment or database changes.
Raw reports and synthetic credentials remain ignored under
`.cloud-runtime/anylist-stress/scale500/` and `scale500-*.json/log` alongside it.

The aggressive 500-user target is **not qualified**. There is a useful local
browse improvement, but it does not turn this VPS into a 500-heavy-user service.
The measured limit is aggregate CPU, primarily in the API processes. These
measurements do not establish an external-provider-only ceiling or prove that
all application architectural improvements have been exhausted.

## Workload and comparison

500 accounts, 200 tracked screen entries/account, 24 games/account, 6,000 screen
titles and 2,000 games. Real authenticated HTTP through matching production
Astro builds, API/read workers, PostgreSQL and normal mapper/enrichment/statistics
jobs. Manual Jellyfin pulls and edits run alongside reads. Provider HTTP bodies
are synthetic with 100ms delay; Jellyfin uses real loopback HTTP with 48 movies
and 60ms delay. CDN transfer, browser paint and live provider quotas are excluded.

The final reference/candidate pair restored the same stopped PostgreSQL data
snapshot before each arm, then refreshed synthetic sessions and primed twelve
hot keys. Both used two API readers, an external catalogue process, one sync
slot, **10 pooled + 10 overflow connections/process**, 16 driver connection
pools, a 3-core quota and 5 GiB memory cap on the 4-vCPU host. Lower CPU/IO
weights and the deployment-health guard remained enabled. Profiling was off.

One later trial launcher used the unrecognized `DATABASE_MAX_OVERFLOW=5` name;
the actual default overflow was 10. Both final comparison arms therefore used
10+10, as their pool peaks also confirm. Earlier 10+5 trials are separate
experiments. Reproduction must use `DATABASE_POOL_OVERFLOW`. The launcher now
records effective non-secret runtime settings rather than relying on labels.

Final mixed levels: `--users 80 160 500 --seconds 40 --think 3.5 --prime
--probe-rounds 24 --client-shards 16 --cold-fraction .04`, with
`STRESS_ACCOUNTS=500 STRESS_LIBRARY_SIZE=200 STRESS_RANKINGS=1` and
`--split-catalogue` before the load flags. Four percent means varying-key
journeys; those keys can become warm through other requests or workers.

| Users | Reference p95 | Candidate p95 | Reference successful req/s | Candidate successful req/s | Reference errors | Candidate errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 80 | .1938s | .1694s | 39.44 | 39.51 | 0 | 0 |
| 160 | 1.6353s | 1.4744s | 59.72 | 61.55 | 0 | 0 |
| 500 | 15.0187s | 15.0108s | 52.16 | 55.74 | 406 (13.67%) | 374 (12.00%) |

Successful req/s includes outstanding-request drain time; p95 includes errors.
At 160, syncs completed by the deadline improved 4/13 -> 6/13; at 500, 0/27 ->
1/30. This remains overloaded. Another candidate repeat had worse 160-user p95
(1.92s versus 1.64s reference); shared-host and background-work variation matters.
Do not describe the modest matched gain as a large capacity increase.

## Retained query improvement

Local popular/trending browse repeatedly extracted JSON ranking values and
sorted the catalogue. Simply adding expression indexes was insufficient:
separate NULL-safe category exclusions made the planner estimate one matching
row where about 4,600 matched, favoring a broad bitmap scan and sort.

The query now uses fixed ranking expressions matching two PostgreSQL indexes,
and combines exclusions into one NULL-safe rejection. The latter preserves the
old truth table, including missing JSON keys and legacy genre shapes. No
provider fan-out, result window, ordering tie-break or private viewer state was
removed. Malformed/overflowing legacy ranking values stay stored and rank as
unknown, so index evaluation cannot break metadata writes.

On the actual VPS catalogue, the first-page default query changed from about
63ms to .4ms in the plan probe. The controlled local 6,000-title SQL benchmark
with default exclusions measured popular/trending ranked medians around
15-16ms -> 1.1ms with matching identities/order. This is not a universal 150x
browse speedup: viewer policies, cached external ranking overrides and deeper
offsets can still select a broad plan. The mixed candidate's aggregate browse
statement averaged 32.5ms in one arm. Further ranking/pagination work remains.

At 80 users in the matched pair, PostgreSQL CPU fell .355 -> .259 cores (27%)
and total lab CPU 1.986 -> 1.821 cores (8%). A local bounded write control
measured 100 metadata updates at 5.67ms with the indexes versus 5.40ms without;
ten measured samples per arm, excluding commit/fsync. This small fixture does
not establish migration or write cost for a production-sized catalogue.

Apply `mt096_browse_ranking_indexes` before starting the updated query. Its DDL
is frozen separately from the application compiler. PostgreSQL alone creates
these indexes; SQLite fixtures retain portable ranking expressions. Migration
upgrade/downgrade/upgrade and actual indexed writes were checked in disposable
PostgreSQL. No deployment schema was migrated.

## Single-user and page-context protection

The proposed full-page split into essential context plus a separate notification
request was rejected: it required two RPCs and seven SQL statements rather than
one RPC/five statements and worsened loaded p95 by roughly 14-15% in the clean
trial. Full pages retain the combined context. Profile fragments request only
essential context (two SELECTs on the ordinary fixture), preserving settings and
poster preferences. Auth redirect routes only validate their session.

Optional notification errors no longer discard usable account context. The app
bar coalesces one fallback notification read per SSR request. Normal full pages
reuse their combined snapshot, with no extra RPC or cross-request private cache.
Session revocation/settings freshness and private/no-store responses remain.

Serial real-HTTP probes, 24 samples/label with ordinary workers active:

| Operation | Reference median / p95 | Candidate median / p95 |
| --- | ---: | ---: |
| Screen page | 56.2 / 68.6ms | 54.5 / 67.1ms |
| Game page | 60.7 / 70.2ms | 59.8 / 72.9ms |
| Profile list | 41.7 / 56.4ms | 40.1 / 54.1ms |
| Browse | 92.2 / 102.8ms | 37.3 / 99.1ms |

No material single-user regression was observed; these short samples cannot
prove the absence of every regression. Browse's tail remains visible.

## Resource ceiling and the meaning of 500 users

At 500 aggressive users, candidate CPU attribution was approximately:

| Component | CPU cores |
| --- | ---: |
| Two API readers together | 1.133 |
| Primary API, including account jobs/proxy | .670 |
| PostgreSQL | .408 |
| Astro frontend | .298 |
| Catalogue process | .200 |
| Load generator | .193 |

The whole lab used 2.941 cores against its 3-core quota; about 82% of quota
periods were throttled. Competing host work used about .26 cores. The lab peaked
at 1.65 GiB while the host retained roughly 14 GiB available; host IO wait was
.2%, and sampled PostgreSQL lock wait peaked at zero in this level. Per-PID
accounting follows surviving process pairs; short-lived PostgreSQL processes
can be undercounted. Core utilization alone was not used as API attribution.

An earlier 10+5-pool, pre-combined-filter resource trial raised the quota from
3 to 3.5 cores. At 500, attempted throughput rose 77.94 -> 91.51 req/s and
p95 fell 15.02 -> 12.56s, but 102 errors remained. This supports a CPU ceiling;
it is not a comparison of the final implementation or proof of linear scaling.

With the final implementation, **500 sessions at 15s mean think time**, over
65 seconds, produced 57.18 successful req/s, 1.1406s p95 and zero HTTP errors.
It completed 42 of 111 admitted syncs by the deadline, with 66 pending at the
last queue sample. This slower foreground workload is plausible, but the
growing sync backlog prevents calling it sustainable overall capacity. Its
longer duration also admits more sync cohorts than the 40-second trial.

The five-minute scheduled account-pull timer is not covered by these short
process lifetimes. Manual pulls and other periodic workers are covered. A long
scheduled-cycle/soak test is still needed before setting an operational limit.

PostgreSQL replacement, more pool connections or more threads are not supported
as the primary solution by these observations. The widest remaining application
target is reusing prepared public metadata projections while attaching focused,
fresh private state, reducing repeated query construction/JSON hydration. Account
workers also need CPU isolation and fair durable queue service at larger load.
These are further architectural projects with invalidation/recovery requirements,
not measured 500-user fixes. Moving the same work to more processes alone will
not remove its CPU cost. Provider quotas need separate live-provider validation.

## Verification and rejected measurements

- Fourteen focused PostgreSQL checks pass: ranking/index plans, legacy category
  parity, malformed data/writes, fixture upgrade safety, essential/full context,
  optional failure, privacy, freshness and revocation.
- 126 paired search/filter/browse samples match identities/order, rows, bytes,
  totals/pagination/pending state, SQL counts and provider requests.
- Fifteen focused frontend SSR/notification/lifecycle checks pass; the final
  production build passes. Desktop/mobile authenticated pages rendered, partial
  responses retain private headers and skip notifications, first/repeated
  nonzero-scroll reloads and history traversal were checked, and startup made no
  duplicate notification/preference requests. Browser errors were empty. Artwork
  URLs and data were synthetic; this does not validate live image providers.
- 125 browse neighbors on a clean database have two failures, one fake-session
  error and two skips, exactly reproduced on the pinned baseline with matching
  configuration. Earlier full discovery also retained existing backend/frontend
  failures; this is not a green full suite.
- Reader replacement preserves active syncs, committed edits and viewer privacy;
  direct reader writes are rejected. Catalogue standby takeover publishes queued
  work, serves warm metadata without new IGDB calls and reads a movie from the
  database with process caches empty.
- Final HTTP/sync calibration passes. All 385 uploaded source/build/launcher
  hashes match the local manifest. The effective configuration file confirms
  two readers, 10+10 pools, one sync slot and external catalogue mode.
- Initial single-pool generator results are diagnostic only: generator CPU
  reached about .67 cores. Partitioning driver pools reduced it to about .19;
  all reported final pairs use the same 16-shard driver.
- Early fixture-upgrade trials corrupted JSON-null cold stubs into arrays and
  were discarded. The upgrade was fixed to touch object-shaped documents only;
  cold/null/array/existing evidence now have a PostgreSQL regression check.
- The final reference/candidate pair's 74 collected deployment guard probes all
  returned 200, worst 76.6ms. Additional trial guards remained enabled. Raw
  state, timings, effective configuration and upload verification are collected
  before cleanup. The stopped private lab, owned local browser/UI servers and
  disposable PostgreSQL container have been removed.
