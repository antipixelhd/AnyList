# CPU, catalogue locks and sync queues

Work is isolated on `codex/anylist-stress-test`. No beta or production deployment.
Baseline backend: `2fdd54ea`. Raw artifacts are ignored under
`.cloud-runtime/anylist-stress/cpu-sync/`.

## Findings and changes

The measured cost is application work as well as database contention. A diagnostic
CPU-sampled primary process spent 15.4% of samples in season reconciliation and
65.3% with SQLAlchemy on its stack. These overlapping stack categories are not
exclusive overhead percentages. Asyncpg appeared in 4.7%; this does not justify
replacing the driver or PostgreSQL. The useful changes remove repeated queries,
hydration and writes before considering a different stack.

* Public identity publication now resolves all incoming identities together,
  batches new bindings while the outer catalogue write lock is owned, and merges
  new root fields before the initial insert. Standalone/savepoint callers retain
  ownership checks; identity evidence and protected fields remain enforced.
* Empty season receipts are consumed in a bounded batch only when there is no
  matching show, existing season state, historical activity or release boundary.
  Every turn reserves capacity for normal reconciliation; later metadata queues
  another receipt through the existing triggers.
* Endpoint rate-limit decorators no longer pay for a redundant global middleware
  route scan. Configured default/application limits retain the original SlowAPI
  middleware. Tests cover client isolation, response headers and binary streaming.
* Media-server pulls have configurable bounded concurrency and serialize by
  account before taking a global slot. Waiters do not hold database sessions.
  A cancelled queued pull is checked after admission and makes no server request.
* Overlapping imports acquire public title/show identities in stable native-ID
  order. A real reversed three-title race deadlocked before this change; both
  accounts now retain their complete collections. Equal show upserts avoid row
  rewrites and correctly return mappings after identical racing inserts.
* Direct cached-film imports allocate collection memberships in batches of at
  most 500. File savepoints remain per item. Unused allocations are removed;
  malformed files cannot create empty memberships or contaminate add-dates.
* Cinema evidence claims/publications use their snapshot row lease without the
  global catalogue identity lock. JSON publication locks media `FOR NO KEY UPDATE`,
  allowing collection foreign-key `KEY SHARE` locks to coexist.
* Migration `mt095_metadata_revision_shards` replaces the global statistics
  invalidation row with 64 transactional shards. Readers use the committed sum.
  This preserves rollback, reverse commit order and repeatable-read cutoffs.
  Visibility changes retain atomic snapshot purges. Apply migration and readers
  together; coordinate any downgrade with worker/application rollback.

The lock choice follows [PostgreSQL's row-lock compatibility and ordering guidance](https://www.postgresql.org/docs/16/explicit-locking.html).
SQLAlchemy's `key_share=True` option renders `FOR NO KEY UPDATE`, including
[refresh's dictionary options](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_0_49/doc/build/changelog/migration_12.rst).
The global-limit fallback preserves [SlowAPI's decorator/middleware contract](https://github.com/laurents/slowapi).

## Controlled local comparisons

`scripts/benchmark_publication.py` used disposable PostgreSQL, pinned baseline
source and the same inputs. These are direct backend microbenchmarks, not user
capacity measurements. Timings are a single local comparison and were collected
alongside other tests; statement counts and semantic fingerprints are the stronger
evidence. Counts below are SQLAlchemy cursor executions (an executemany counts
once); transaction savepoints are included where stated.

| Operation | Before statements | After statements | Before Python CPU | After Python CPU |
| --- | ---: | ---: | ---: | ---: |
| 100 cold identity publications | 1,200 | 400 | 0.359 s | 0.172 s |
| 100 warm identity publications | 800 | 300 | 0.297 s | 0.109 s |
| 20 empty season receipts | 200 | 12 | 0.109 s | 0.031 s |
| Import 100 cached films, new memberships | 506 | 308 | 0.250 s | 0.078 s |
| Repeat same 100-film import | 206 | 206 | 0.094 s | 0.063 s |

Identity and collection fingerprints match, with 100 roots/300 bindings and 100
files respectively. Both season runs completed all 20 jobs. Provider calls: zero.
Cached import wall time fell 644 to 451 ms; the unchanged warm path measured 350
versus 358 ms, so there is no demonstrated warm-import latency improvement.

The paired search benchmark has 108 samples over screen/game searches, cinema,
people/contributors, game browse and profile windows/activity. Every sample matches
on ordered identity fingerprint, rows, totals, pending state, payload bytes, SQL
reads/writes and provider calls: aggregate 1,130 reads, 322 writes, 250 synthetic
provider calls and 1,721,545 payload bytes in each run.

## VPS evidence and outstanding comparison

Fresh disposable PostgreSQL instances, identical frontend build, two API readers,
separate catalogue owner, 10+5 pool per process, 400 synthetic accounts, 4% varying
keys, 3.5-second mean think time, 40-second levels. The whole lab has a three-CPU
quota, including the load generator, PostgreSQL, Astro and synthetic upstream.
The real HTTP/auth/API/SQL paths run; providers are delayed synthetic responses.

The first candidate included admission, ordering, identity batching, season and
middleware changes. It preceded collection batching, the final root insert change,
cinema lock changes and revision sharding:

| Users | Baseline p95 | First candidate p95 | Baseline syncs completed | Candidate syncs completed |
| --- | ---: | ---: | ---: | ---: |
| 40 | 216 ms | 175 ms | 4/4 | 4/4 |
| 80 | 283 ms | 200 ms | 7/7 | 7/7 |
| 120 | 1,183 ms | 921 ms | 5/10 | 8/10 |
| 160 | 3,384 ms | 3,834 ms | 2/14 | 4/14 |

Zero HTTP errors in both runs. This exposes a queue-throughput/tail-latency
tradeoff at saturation, rather than an across-the-board capacity win. Reader
restart/private-edit/sync preservation and catalogue owner failover/publication
probes passed for this candidate. The baseline had a shutdown-only telemetry bug
after its timed stages and recovery probes; that instrumentation was corrected.

Per-PID CPU counters, with 100% meaning one CPU, attribute primary API use at 80
users to 65.0% before and 51.6% in the first candidate; readers together used
65.1% and 62.8%. At 160 the whole lab consumed about 285% of its 300% quota and
was frequently throttled. PostgreSQL used approximately 43–44%, substantially below
one CPU. PostgreSQL values are lower bounds when short-lived backends fall between
samples. RAM pressure and disk reads were not the demonstrated limiting factor.

The first candidate still spent substantial time waiting for catalogue writes.
The primary's 100 catalogue lock acquisitions all came from cinema refreshes,
with a 4.3-second maximum hold. Catalogue process maximum hold was 6 seconds.
Separate real PostgreSQL tests now reproduce and remove the unrelated statistics
counter serialization and verify cinema publication while catalogue and foreign-key
locks remain held. These tests establish the locking behavior, not a measured VPS
latency reduction from the final fixes.

The final candidate was uploaded to the isolated lab, migrated, and passed its
HTTP/full-sync startup smoke. Its timed run started, but Tailscale required SSH
reauthentication before results could be collected. **Final VPS results, the
one-slot versus two-slot comparison, and remote artifact cleanup remain pending.**
The systemd lab has a finite runtime and a separate production health guard. This
report does not establish 1,000-user capacity or a provider-only ceiling.

## Verification

The focused PostgreSQL/unit run completed 163 checks with two existing fixture
errors: an intentional legacy duplicate conflicted with the fixture's newer
unique index, and an mt050-only rebuild was queried with a newer full ORM shape.
Both fixtures were corrected and their replay plus two revision tests passed.
The other 161 focused checks passed. Five additional real PostgreSQL sync tests
cover deadlock ordering, no-op show races, invalid-item/batch/date behavior and
queued cancellation; five cinema cases cover caching, retries and locking.

Full unit discovery: 3,668 tests, one failure, 68 errors, 1,230 skipped. Failure
identities match the pre-change run exactly (existing fixture/fake/SQLite issues
and the existing parent-proposal assertion). An initial run under Windows sandbox
temporary-directory restrictions added file-test failures; the repeat with a
writable temporary directory returned to the baseline failure set. Ruff and
`git diff --check` pass.
