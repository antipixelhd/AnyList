## Ratings

Scores use an ordinal scale from 0 to 10. **10** means the behavior consistently meets the criterion in the sampled paths. **8** means it works with a visible exception. **6** means the experience is mixed across ordinary paths. **4** means the issue regularly disrupts the interaction. **2** means the user loses feedback or usable content. The follow-up target is **9.5 per category and device**, with missing device coverage left unscored.

## Skeleton timing reference

Google’s AndroidX `ContentLoadingProgressBar` illustrates two independent decisions. Its implementation waits 500 ms before showing the progress indicator and gives a visible indicator a minimum of 500 ms to avoid a flash. The AndroidX numbers apply to that progress bar. Material 3 describes motion schemes and leaves web skeleton timing to the application. [AndroidX API behavior](https://developer.android.com/reference/androidx/core/widget/ContentLoadingProgressBar) · [AndroidX timing implementation](https://android.googlesource.com/platform/frameworks/support/%2B/f2e05c341382db64d127118a13451dcaa554b702/core/core/src/main/java/androidx/core/widget/ContentLoadingProgressBar.java) · [Material 3 motion](https://m3.material.io/styles/motion)

AnyList’s shared reveal starts **after the content is available**. It triggers after a wait of at least 100 ms and animates opacity from 0.6 to 1 over 120 ms. That 100 ms is an eligibility threshold for the reveal. The Browse skeleton’s minimum visible time is currently 0 ms. The detail and profile frames replace their pending regions as the destination commits. The detail tab exit delay is a separate behavior.

For a later comparison, record the time the placeholder first paints, its visible lifetime, the time ready content becomes usable and when the visual effect settles. A fast or cached hit earns full credit when it skips the skeleton. A minimum should be evaluated on the placeholder’s own visual treatment, with ready text and controls available immediately. Compare the existing static silhouette on dense lists and grids, a localized shimmer or gentle pulse for slow artwork, and the existing short reveal when an asynchronous section settles. This baseline rates the shipped variants.

## Reproducing the baseline

- Chrome 157 on Windows, 1440 × 960 desktop and 390 × 844 mobile emulation at 2× device pixel ratio. Used Chrome DevTools Performance traces, CDP filmstrips, animation and layout sampling, and browser touch dispatch for visible mobile targets. Offscreen controls and input tests used DOM events.
- The 480 ms gate held delivery of selected real responses in the browser for at least 480 ms from the request start. Slower responses ran to completion. The unheld runs preserved ordinary network timing. Cold runs bypassed or cleared the browser HTTP cache. Warm runs used AnyList’s existing history, result and retained panel caches.
- One cache-bypassed Home trace measured 449 ms LCP and 0.00 CLS on desktop. One mobile-emulated Elden Ring trace measured 409 ms LCP. These are individual lab reloads. The interaction numbers are sample observations and depend on viewport, route and cache state.
- Chrome DevTools tracing and emulation worked. Chrome’s Animations panel can replay and slow CSS and Web Animations for visual inspection. CDP screenshots and timing samples provided the frame-by-frame evidence here. Physical handset and Safari behavior, and network-failure or retry paths, remain unscored.
