# Stage Two loading and transitions: implementation design

Status: design reference, 2026-09-21. The local implementation and verification handoff is recorded in the [Stage Two acceptance contract](STAGE-TWO-PLAN.md). This document does not claim owner approval of a visual build or deployed verification. The supplied [AniList Browse skeleton screenshot](references/anilist-browse-card-skeleton-2026.png) is a visual reference, not a claim about AniList's internal code.

## Experience contract

Navigation should feel immediate without briefly showing wrong or incomplete data. Keep the app bar, page width, profile navigation, filters, and already-valid content stable. Reserve the exact geometry of data that is not ready, then reveal complete content with a short opacity fade. Never show a false empty state, a stale result under a new query heading, or a dialog whose fields fill in after opening. Loading belongs to the affected region; only a delayed **navigation** may use the thin top-edge progress line. The line is fixed/overlaid, never takes layout space, and never claims an exact percentage.

The working model is:

```text
intent → show cached/retained data if valid → request missing/stale data
       → if brief: commit complete result directly
       → if delayed: show geometry-matched placeholder in affected region
       → success: atomically commit result, then short fade
       → settled empty / error / confirmed offline: show that region's true state
```

For an explicit refresh with old data, keep the old data visible and mark the region busy rather than replacing it with skeletons. For a *different* query/filter, old data may remain only if clearly associated with its old heading/filter; otherwise reserve the result region with skeletons. Do not keep a spinner alive merely to satisfy an animation duration. A visible placeholder can complete its fade-out, but content should not be artificially delayed to make the placeholder noticeable.

### Shared timing and visual tokens

These are initial design values, to be centralized as CSS/TypeScript tokens and adjusted by local visual measurement, not copied into each page:

| Element | Initial behavior |
| --- | --- |
| Loading threshold | No visual loading chrome for work resolving within about 150 ms. Start a scoped placeholder or top line only after the threshold. |
| Top progress | Fixed at viewport top, 2 px, delayed about 150 ms for route navigation only; indeterminate motion with a finite, gentle finish on resolution. Hide/cancel on superseded navigation. |
| Visible skeleton | No forced wait before showing real content. If already visible, use a roughly 120–180 ms cross-fade so it does not blink off. Do not impose a 400 ms minimum that slows warm-cache navigation. |
| Content reveal | Opacity 0→1 over roughly 140–200 ms. For card collections, optional 20–35 ms per-card stagger capped at 150 ms total; never delay the whole grid proportional to result count. |
| Editor entrance | Fully populated dialog fades in and scales approximately 0.98→1 over 160–200 ms, without animating its final width/height. Exit may be shorter. |
| Skeleton shape | Static, low-contrast blocks by default. If shimmer is used, keep it subtle, nonessential, and disabled for reduced motion. Poster blocks hold their actual aspect ratio; text bars hold line height and approximate width. |
| Reduced motion | No translation, scaling, shimmer, or stagger; immediate or very short opacity changes. Busy and error semantics remain. |

Use design tokens for poster aspect ratio, row height, card gaps, header heights, and dialog dimensions so placeholders match the real responsive layout. Image containers retain width and aspect ratio through decode/failure. Font loading, scrollbar appearance, error text, and app-bar state must not move the page horizontally. Prefer `scrollbar-gutter: stable` where appropriate; specifically verify Social and movie/series navigation at short and long page heights.

## Navigation architecture and scope

Current `Tracker.astro` and `TrackerSettings.astro` render full HTML documents. Most canonical pages `await` API data in Astro frontmatter before responding. Therefore, adding skeleton markup *inside those SSR responses alone* cannot make an in-flight navigation visible: the browser cannot show it until the response arrives. Current inline scripts also bind once and several mutations call `location.reload()`. A global client-router switch is **not** a cosmetic change.

Implement navigation in a compatibility-gated slice:

1. Keep server rendering and access control authoritative for first load, refresh, and uncached navigation. Provide a delayed, overlaid top line on navigation from an already-open tab, with no fake blank page. Preserve the current page until the destination is ready.
2. Reuse retained per-tab read-only route data/page view for previously visited canonical routes. Render it immediately, then validate in the background when online. Partition private entries by AnyList user and purge on explicit logout/account switch. Do not cache tokens, credentials, secrets, or write responses. For uncached routes, a shared shell plus route-shaped placeholders requires a client navigation/shell implementation; if that cannot be made safe in Stage Two, the top line plus atomic SSR swap is the acceptable interim behavior, not a misleading skeleton that appears only after the wait.
3. Evaluate Astro's `ClientRouter` on a bounded route set (`/home`, `/browse`, `/title/*`, profile routes, `/recent-events`, then settings). Astro documents `astro:before-preparation`, `astro:after-preparation`, `astro:before-swap`, `astro:after-swap`, and `astro:page-load`; the former can start navigation feedback and the latter can reinitialize page listeners. Audit every one-time listener, dialog, chart, scroll observer, timer, pending fetch, auth redirect, and `location.reload()` before expanding it. Keep native full-document navigation as fallback. See [Astro's view-transitions guide](https://docs.astro.build/en/guides/view-transitions/).
4. Do not attach a cross-route view transition to every card or animate large page geometry. Shared app bar/profile tabs may remain visually continuous; content should swap atomically at stable coordinates. Preserve history, scroll restoration, anchors, focus, keyboard activation, and browser back/forward. A failed destination leaves the previous page usable with a retry/error path.

The per-page rules below are UX requirements independent of which navigation technique passes the compatibility audit. Legacy redirect routes need no duplicate skeleton system. Login/OIDC, logout, account switch, and privileged security flows may deliberately use ordinary document navigation and must never be served from a private cached page.

## Per-page and component rules

| Surface | Stable frame and delayed placeholder | Commit, empty, failure, and interaction rules |
| --- | --- | --- |
| Home `/home` | App bar and title remain; feed cards use avatar/date/text-line geometry; notification/shortcut summaries get their own small placeholders. | Feed empty state appears only after successful empty response. A failed feed shows an in-region retry, not a quiet-feed message. Do not hold the whole page for optional preference/notification summary data. |
| Browse `/browse` | Heading, search field, media-type selector, and grid columns remain. Use dark poster rectangles plus short title bars matching the supplied reference and the real card aspect ratio; keep the count of initial placeholders bounded to visible rows. | Debounced query/type changes cancel older requests. Atomically update heading, URL, and cards for the winning request. A warm result skips skeletons; a delayed different query uses grid placeholders, not an early “No matching titles.” Empty, server error, and offline are distinct settled states. Cards may fade in quickly without moving neighbors. |
| Title `/title/:id` | Reserve hero/poster, facts, action row, description lines, social ratings, and season/episode panels independently; do not blank the full detail surface for a late optional panel. | Do not render Favorite/Library with a guessed opposite state before its own data is known. Local Library action changes the button immediately without reload or adjacent success/pending copy; only local save failure appears at the action and remote failures go to Notifications. Episode refresh shows progress in that panel. Poster decode/failure never changes hero geometry. |
| Profile overview `/user/:name` | Keep `ProfileHeader` and tab rail stable; highlights, activity rows, and favorite cards have separate placeholders. | Public/private/not-found states follow backend response, not a skeleton timeout. Omit absent favorite section after a successful empty response. Profile navigation must retain the same horizontal coordinate. |
| Movie, series, combined lists `/user/:name/{movies,series,list}` | Preserve profile header, filter rail, column headers, row dimensions and scrollbar. Use compact row skeletons with thumbnail, title and metadata bars for uncached lists; retain known rows during same-list refresh. | Filter/sort/view changes on already loaded entries are synchronous and get **no** loader. Section navigation swaps only when destination is ready. Entry counts/empty message update after committed data. Increment, status, rating and other row actions update the affected row in place; no whole-page reload/flash. The owner list response is the editor data source. |
| Library `/user/:name/library` | Profile header remains; membership cards use the same grid/poster skeleton as Browse, sized for Library. | A locally saved item is visible even without connections. Empty means no local membership, not “connect a service.” Refresh/failure cannot make saved local membership briefly disappear. |
| Social `/user/:name/social` | Profile header, search control, Following/Followers headings and two-column geometry remain. Search results use person-row placeholders; existing lists remain visible during search. | Search no-match is shown only after a completed search. Follow/unfollow updates its button/count/list locally on success or rolls back on failure, without reload. No rightward page shift when entering Social from another profile tab. |
| Stats `/user/:name/stats` | Profile header, controls, highlight tiles and chart frames keep fixed heights. Highlights use numeral/text bars; charts use quiet chart-frame placeholders, not fake data. | Media/year change retains old chart *with old selection clearly identified* until replacement is ready, or shows chart-frame placeholders for the new selection. Destroy old Chart.js instances only at commit and clean them up on route exit. Error stays within Stats; empty dataset renders truthful zero/empty charts. |
| Notifications `/recent-events` | Keep page header and group headings; use notice-card/queue-row placeholders by section. | “All caught up” only after successful empty fetch. | Admin and auth routes | Use current document-navigation/security pattern; at most a delayed navigation line before leaving the app shell. | No private offline replay, cached credential form, fabricated skeleton of protected data, or global router interception of OIDC/logout redirects. |

### Cross-page overlays and inline controls

- **Fast search (desktop):** opening shows the input-only dialog immediately and focuses the input. Query work is debounced and superseded requests are aborted/ignored. Never display a transient visible “Searching…” card or an empty/no-match card while pending. If delayed, use the top edge of the dialog or the shared top line as quiet progress without moving content. Movies and Series result sections for one query appear together once both settle; do not mix request generations. Show a settled no-match/error message, and announce the result count or error once to assistive technology. Keep its existing phone boundary unless a separate mobile design is approved.
- **List editor:** from an owner list, retrieve the entry from the retained list payload and construct the complete form *before* calling `showModal()`. One dialog entrance, with stable final size; no “Loading entry…” frame. Outside a loaded list, use a cache hit or fetch before opening, with a local busy affordance on the invoking button if delayed and an error at that trigger if unavailable. Do not fetch the title again on every open. Preserve the opener for focus restoration, even if a route change or save occurs. Universalize this ready-then-open pattern for later list editors. Save controls show only their own busy/error state; offline saves are not queued.
- **Quick rating:** no page skeleton or global navigation line. Touch hold/drag previews the selected star amount; release/tap commits as specified in the Stage Two contract. Optimistically update only the rating display once the action is accepted, with rollback/error if save fails. Preserve confirmation dialog, keyboard focus, and reduced-motion behavior.
- **Increment/status/Favorite/Library/follow controls:** one action must not repaint the route. Prevent duplicate writes, maintain the previous value for rollback, and update just the affected state. A DB failure is local; remote delivery is asynchronous and reported through persisted Notifications where applicable. Ordinary offline edit attempts get a toast, not a Notification.

## State ownership, caching and failure policy

Every async region needs an explicit key: AnyList user (or public), route, query/filter, and data version. Response generation IDs or `AbortController` prevent a late result from overwriting newer input; aborted requests do not show errors. A successful empty array is different from request failure, and an incomplete provider/API response is not an empty list. Cache the read-only data needed to recreate already visited pages and editor views for this tab, rather than DOM fragments with active event handlers. Share poster URLs with browser HTTP caching where possible; do not copy image blobs into application memory without a measured need.

Offline behavior follows [ADR-022](DECISIONS.md): only navigation within an already-open tab is promised. Show retained content immediately. If a previously unseen region cannot fetch, reserve its shape briefly, then show “No internet access” with retry **in that region** once offline is confirmed; do not replace the entire app with `/offline.html`. A first load or refresh offline may produce the browser's normal network page. `navigator.onLine` is a hint, not proof: distinguish network failure from HTTP error and use a bounded timeout/retry path. Offline write attempts remain unqueued and produce a nonpersistent toast; consider a single unobtrusive connection-lost toast while avoiding repeated duplicates. Explicit logout/account switch invalidates all that user's private in-tab entries before rendering the next identity. No local storage of credentials, tokens, API keys, private settings secrets, or auth-only HTML.

The current service worker caches assets and an offline fallback but not page/API/image data. Do not reinterpret that as an existing read-only route cache. Stage Two's in-tab cache can live in application memory; persistence beyond the tab is not required by this contract. If a router or HTTP cache is added, preserve browser refresh/first-load behavior and enforce the same privacy partition.

## Accessibility, responsive layout and observability

Skeletons are `aria-hidden` and cannot receive focus. Mark only the affected result region `aria-busy`, not the whole page; restore it on success, error, abort, and offline. Avoid live announcements for every keystroke or animation. Announce settled result count, no-match, and actionable errors once. A navigation progress line is decorative to screen readers; the destination's heading and focus provide completion. Keep visible focus on persistent navigation, move focus to a new route heading only where normal navigation semantics require it, and return modal focus to its opener. Do not trap focus in a loading region. Preserve contrast and layout in 320 px and 390 px widths, desktop, high zoom, light/dark modes where supported, and `prefers-reduced-motion`.

Measure route intent→usable content, skeleton incidence, real content layout shift, image decode time, cache hit ratio, duplicate fetches, and memory growth over repeated navigation. Avoid turning skeletons into an excuse for slower requests. Inspect actual browser Performance/Network traces before choosing final timing. The companion Astro performance report remains a separate Stage Two deliverable, including image-size tiers and a visualization; this design does not claim those measurements.

## Implementation sequence and acceptance reference

1. Create shared loading tokens, top-line state, skeleton primitives (poster card, compact list row, person row, notification row, text/metric/chart frame), and a request-generation helper. Verify matching geometry and reduced motion before applying them broadly.
2. Implement retained list/editor payload and ready-then-open dialog; remove per-open fetch. Implement Browse/Fast-search/Stats scoped request states and stale-response handling. Remove gratuitous full-page reloads from ordinary actions as each surface is touched.
3. Prototype compatible in-tab navigation on one canonical route pair. Audit event setup/teardown, modal state, scroll, history, auth, and error fallback. Expand only after those checks pass; otherwise retain SSR navigation with delayed top-line feedback and document the remaining client-navigation gap.
4. Add user-partitioned read-only in-tab route/data cache and localized offline behavior. Test logout/account switching and sensitive settings exclusion before widening cache coverage.
5. Apply and visually tune the matrix across every canonical route, including short/long lists and slow images. Record browser evidence and update Stage Two gates; do no VPS verification until all local gates pass.

Acceptance scenarios for each affected surface: warm/instant response shows no flickering placeholder; delayed response shows only the correctly shaped region; rapid query/route changes cannot display stale results; empty, HTTP failure, and genuine offline are distinct; a missing image cannot shift layout; back/forward and repeated open/close do not duplicate listeners; screen reader/busy/focus behavior and reduced motion pass; 320/390 px phone and desktop widths have no horizontal shift; an already-open tab can revisit cached safe pages offline but cannot edit offline; explicit logout prevents the prior user's private content from resurfacing. This is local acceptance work, not a deployed/real-device claim.
